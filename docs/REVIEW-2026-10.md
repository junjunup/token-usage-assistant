## 3. 风险体检（按严重程度）

### 3.1 高

**H1 · Electron 安全公告：当前 44.4.4 受影响，需升到 ≥ 44.9.1**【已核实】
- 证据：`package.json` 锁定 `electron: 44.4.4`（2026-09-22 发布）。`gh api repos/electron/electron/security-advisories/GHSA-jr5w-w6x2-84p9`：severity **high**，2026-10-22 发布，受影响范围 `>= 44.0.0-alpha.1, < 44.9.1`；内容是阻止一组被攻破的 eMudhra 中间证书，同时覆盖 Chromium 网络栈与 Node 的 `tls` / `https` / `fetch`；公告写明「没有应用侧绕过，必须升级」。44.x 线现在最新是 44.9.3（10-21），45.0.0 也已发布（`pnpm view electron time`）。
- 与本项目的关系：所有平台请求和检查更新都走 `net.fetch`（`desktop/main.cjs:914`、`:1020`），请求头带 Bearer API Key。能截获网络流量、并持有这批证书签发的证书的攻击者，可以冒充平台接口，拿到密钥、喂假额度。现实利用门槛较高，但这正好落在本项目「凭据」这条最重要的红线上。
- 附带问题：仓库的 Dependabot 告警是关闭的（`gh api repos/.../dependabot/alerts` 返回「Dependabot alerts are disabled」），公告不会自动提醒。
- 与现有规则的冲突：T1.3 要求依赖「选用至少发布两周以上的确定版本」，44.9.1 只发布了 3 天。→ Q1。
- 建议：升到 44.9.x（只升补丁线，不跨大版本），走一次完整的 Release（两个平台打包 smoke + Windows 升级验证），作为 1.9.0-beta.3；在 GitHub 打开 Dependabot **告警**（不必开自动 PR）。代价：小（代码一行，加一次发版）。注意：升级可能影响 T7.7 记录的「内容保护关不掉」这个 Electron 行为，smoke 已覆盖这一项。

**H2 · 偏好会被「不认识它的版本」永久删除（包括当前版本）**【已核实】
- 证据：`desktop/store.cjs:67-78` 读取设置时逐键调用 `patchSettings`，`desktop/domain.cjs:324` 对 `DEFAULT_SETTINGS` 里没有的键抛出「不支持的设置」，被 catch 后丢弃；`desktop/store.cjs:80-81` 保存时只写内存里的已知键。`desktop/main.cjs:162-180`：窗口每次移动或改大小，350 ms 后就保存一次。所以只要旧版本运行时动一下窗口，新版本的偏好就从文件里消失了。值不合法的已知键（例如将来某个版本给 `refreshSeconds` 加了 600）也一样会被重置。
- 实际发生过：计划第 5 节 10-18「LaunchServices 选中旧开发包」一条——旧版重写 `settings.json`，丢了 `updateCheck` 和 4 个菜单栏偏好。
- 文档：CHANGELOG 第 19、25 行只说「旧版会跳过……其余设置不受影响」，没有说跳过的设置会被删掉、重新升级后回到默认值。升级验证脚本只检查「旧版能读」（`scripts/verify-upgrade.cjs:471-482`），不检查「旧版保存一次后再升级」，所以测不出来。
- 影响：目前只是偏好（不涉及凭据和数据），默认值也合理，所以损失不大；但随着设置项增多会越来越明显，而且文档说法会误导回滚判断。

- 证据：`desktop/claude-collector.cjs:132-139` 第一次连接时在 49152–65151 里随机选一个端口写进 `collector.json`，之后一直用它；`:218-226` 监听失败只把状态置为 `stopped` 并抛出，不换端口；`desktop/main.cjs:922-930` 启动失败时提示「Claude 本地采集端口不可用，请重启或重新连接」，但重新连接会读回同一个 `collector.json`（`prepare()`，`:119-131`），重启也是同一个端口。

**M5 · 「首次启动图标卡住」（T7.12）与「首跑 smoke 150 秒」的关系**【分析】

- **L5 · 检查更新失败后 24 小时才重试**【已核实】：`desktop/update-check.cjs:100-117` 对 403 / 网络错误静默并在下一个 24 小时周期重试，与 T5.2 设计一致，没有问题；10-18 日志里的一次失败和一次 403 都属于这种情况。唯一可改进的是网络环境差时可以缩短首次失败后的重试间隔，价值不大。
- **L6 · 前端单个 JS 包 682 KB**：Vite 有提示，对本机应用影响很小，不建议花时间。
- **L7 · Claude 导出文件没有轮转**：`usage.jsonl` 只追加不清理，每次查询从头读（`desktop/claude-collector.cjs:343-400`，在 worker 线程里）。长期使用会越来越大，这是 T4.2 的真实理由之一（第 4 节）。

### 3.5 核对过、没有发现问题的部分

- 数据红线：缺数据显示「—」（托盘、通知、面板、菜单栏、诊断导出均核对）；失败时保留上次成功值与时间（`desktop/monitor.cjs:76-128`）；USD / CNY 分开（托盘按币种逐行、分析按币种汇总 `desktop/tool-analytics.cjs:451`）；历史差值只对同一账期内单调递增的用量计数器计算，不是余额差（`desktop/analytics-core.cjs:290-318`）；面板三格只取账户接口数据，本机工具统计不进面板；余额账户在用户设阈值前不发告警。
- 隐私：诊断导出只取白名单字段（`desktop/diagnostics.cjs`），日志有字段白名单与脱敏（T3.2 测试覆盖）；Codex 只调用 `initialize`、`initialized`、`account/read`（`refreshToken:false`）、`account/rateLimits/read` 四个方法（`desktop/codex-rpc.cjs:171-190`）。
- 安全：主窗口、悬浮窗、面板、隐藏渲染窗口都开了沙箱与上下文隔离、关闭 Node；拒绝新窗口和导航、拒绝权限请求；IPC 校验发送方与主框架地址，面板只能调 5 个通道（`desktop/main.cjs:450-470`）；自定义协议带严格 CSP（`connect-src 'none'`）；外链地址只来自平台注册表常量。
- 升级与回滚的其余部分：凭据、窗口位置、历史（回滚后只能看到迁移时刻之前的历史，CHANGELOG 已写）、Codex 未验证版本缓存（CHANGELOG 已写）都与文档一致。另有一个小缺口：回滚期间旧版写进 `history.json` 的采样，重新升级后不会导入（数据库里已有该账户的数据），会留一段空档（10-18 已观察到约 1 分钟）；只写在计划第 5 节，CHANGELOG 没写。
